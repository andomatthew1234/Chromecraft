# Electron 44.7.2 extension compatibility research

Research date: 2026-10-21  
Target: Chromecraft on Electron 44.7.2 / Chromium 152.0.7977.149  
Scope: APIs needed by mainstream Manifest V2 and Manifest V3 Chrome extensions

## Executive conclusion

Stock Electron cannot truthfully promise that every Chrome extension works. Electron's own documentation says that it supports only a subset of Chrome's extension APIs, that arbitrary Chrome Web Store extensions are unsupported, and that perfect Chrome compatibility is a non-goal. It loads only unpacked extensions, only in persistent sessions, and the application must load them again on every launch ([Electron 44.7.2 extension documentation](https://github.com/electron/electron/blob/v44.7.2/docs/api/extensions.md)).

Electron 44.7.2 is nevertheless a better base than the public support table suggests. Its exact-version test suite proves that MV3 extension service workers register, start, restart, and exchange `chrome.runtime` messages. The same suite exercises more `chrome.tabs` methods than the public documentation promises. Those capabilities are real in this version, but anything absent from the documented support table remains provisional under Electron's stated contract ([Electron 44.7.2 extension tests](https://github.com/electron/electron/blob/v44.7.2/spec/extensions.spec.ts)).

Broad compatibility therefore requires three layers:

1. Use Electron's native extension implementation for MV2/MV3 backgrounds, content scripts, runtime messaging, `storage.local`, `scripting`, and `webRequest`.
2. Implement browser-owned adapters for UI and browser-model APIs Electron does not own: actions and popups, commands, context menus, tabs, windows, downloads, cookies, side panels, and portions of identity.
3. Patch or replace Electron/Chromium for browser-process behavior that cannot be faithfully supplied through public Electron APIs, especially Chrome-specific WebAuthn decisions, complete Declarative Net Request behavior, Chrome-profile identity, and some private or platform-integrated APIs.

This report uses **supported** only when Electron documents the capability or its v44.7.2 source tests prove the exact behavior. **Provisional** means exact-version source evidence exists but Electron does not promise the API publicly. **Unsupported** means Electron documents the gap or its source explicitly disables/stubs it. **Uncertain** means a manifest permission/key may parse or a Chromium implementation may be compiled in, but there is no Electron support contract or adequate exact-runtime evidence.

## Baseline and support boundary

- Electron 44.7.2 embeds Chromium 152.0.7977.149, Node 24.21.0, and V8 15.2.124.37 ([Electron 44.7.2 release record](https://releases.electronjs.org/release/v44.7.2)).
- Electron's documented supported API surface is limited to DevTools APIs, selected `chrome.extension`, selected `chrome.management`, selected `chrome.runtime`, all `chrome.scripting`, `chrome.storage.local`, selected `chrome.tabs`, and all `chrome.webRequest`. APIs not in this list are explicitly provisional even if they happen to work ([tagged Electron support table](https://raw.githubusercontent.com/electron/electron/v44.7.2/docs/api/extensions.md)).
- Loading is directory-based: `.crx` files cannot be passed to `loadExtension`. Chromecraft may download and verify a CRX, but must unpack it before calling Electron. The session must be persistent and the extension must be reloaded on every boot ([tagged `Extensions` API](https://raw.githubusercontent.com/electron/electron/v44.7.2/docs/api/extensions-api.md)).
- Electron logs load warnings when a requested API is unsupported. A successful `loadExtension()` therefore proves only that the package parsed and loaded; it does not prove functional compatibility ([tagged `Extensions` API](https://raw.githubusercontent.com/electron/electron/v44.7.2/docs/api/extensions-api.md)).
- Chrome's current API reference assumes a complete browser product: browser windows and tabs, toolbar actions, profile/account services, downloads, native-host registries, policy, and Chrome-owned UI. Electron is an embedder and intentionally does not provide many of those product concepts ([Chrome Extensions API reference](https://developer.chrome.com/docs/extensions/reference/api)).

## MV3 service workers and compatibility shims

MV3 workers are not the blocker they were in older Electron releases. Electron 44.7.2's own suite proves worker startup and message delivery. Electron also exposes Session preload registration with a `service-worker` target, and its exact-version documentation confirms service-worker preload scripts as a supported context ([Electron 44.7.2 preload registration](https://raw.githubusercontent.com/electron/electron/v44.7.2/docs/api/structures/preload-script-registration.md), [Electron 44.7.2 Session API](https://github.com/electron/electron/blob/v44.7.2/docs/api/session.md#sesregisterpreloadscriptscript)). This provides a possible IPC bridge for missing APIs in workers.

That bridge is not automatically a complete or safe extension API system:

- A service-worker preload applies at the Session level, so it must identify extension scopes and reject ordinary website workers.
- Each request must carry an extension identity derived from trusted browser-process state, never a caller-supplied ID.
- The main process must re-check manifest permissions, host permissions, active-tab grants, tab/window ownership, and argument schemas.
- Events must wake dormant workers and preserve Chrome's listener-registration and disconnect semantics.
- Electron 44's public API does not document a general supported mechanism for replacing native `chrome.*` bindings in every extension execution world. The earlier Electron design issue explains why extension isolated worlds are distinct from ordinary preload worlds ([Electron issue #22285](https://github.com/electron/electron/issues/22285)). Every injected namespace therefore needs an exact-runtime proof, not an assumption.
- Electron's security guidance warns against exposing raw `ipcRenderer`; expose one validated method/event surface per capability ([Electron IPC tutorial](https://www.electronjs.org/docs/latest/tutorial/ipc), [context isolation](https://www.electronjs.org/docs/latest/tutorial/context-isolation)).

The correct implementation is a permission-aware extension bridge, not an unrestricted IPC tunnel.

## Action popups are two separate compatibility problems

Rendering `popup.html` in an anchored Chromecraft surface solves only the visible half of `chrome.action`. Chrome also maintains per-extension and per-tab title, icon, popup URL, badge text/color, enabled state, pin state, `onClicked`, and programmatic `openPopup`. Electron 44.7.2 implements these calls as no-ops or dummy returns. A popup can appear while an extension is still functionally broken because its worker cannot update the badge, change the popup, disable the action, or receive clicks.

An authentic shim must therefore:

1. Parse MV2 `browser_action`/`page_action` and MV3 `action` defaults.
2. Store global and per-tab overrides and delete per-tab state when a tab closes.
3. Render live title/icon/badge/enabled state in the browser shell.
4. Resolve the active tab and grant `activeTab` only after a qualifying user gesture.
5. Open a sandboxed extension page using the same persistent extension Session, size it to Chrome's documented bounds, and close it on focus loss.
6. Dispatch `onClicked` only when no popup is configured.
7. Bridge the complete `chrome.action` and legacy aliases into both MV2 pages and MV3 workers.

Chrome documents these UI and event rules in the [Action API](https://developer.chrome.com/docs/extensions/reference/api/action) and [popup guide](https://developer.chrome.com/docs/extensions/develop/ui/add-popup).

## Passkeys and WebAuthn: three different mechanisms

### 1. Page WebAuthn and the operating-system prompt

An ordinary website calls `navigator.credentials.create()` or `get()`. On Windows, Chromium can hand the ceremony to the Windows WebAuthn platform, which explains why an Electron browser may show the Windows passkey dialog. That is page WebAuthn behavior, not proof that a password-manager extension received the request.

### 2. Password-manager extension interception

Bitwarden documents that its browser extension replaces the page's native `navigator.credentials.create` and `get` methods with an injected implementation, while retaining a fallback to the native browser behavior ([Bitwarden browser-extension passkey architecture](https://github.com/bitwarden/contributing-docs/blob/main/docs/architecture/deep-dives/passkeys/implementations/provider/browser-extension.md)). That path depends on reliable document-start injection, web-accessible resources or MAIN-world scripting, runtime ports/messages, a live MV3 worker, storage, and extension popup/window UI. Electron supplies several foundations, but missing action/window behavior or a failed bridge can cause Bitwarden to fall through to Windows.

This path is browser-shimmable and should be tested as a full ceremony, not by checking that content scripts loaded.

### 3. WebAuthn initiated by an extension page

Some flows, including signing into or unlocking the password manager itself, call WebAuthn from an extension page and assert an RP ID covered by host permissions. Chromium implements the extension-specific RP-ID authorization in Chrome's `ChromeWebAuthenticationDelegate`; its source checks that the caller is an enabled extension and that it has suitable host permission ([Chromium Chrome WebAuthn delegate](https://chromium.googlesource.com/chromium/src/+/main/chrome/browser/webauthn/chrome_web_authentication_delegate.cc), [Chromium tests](https://chromium.googlesource.com/chromium/src/+/main/chrome/browser/webauthn/chrome_web_authentication_delegate_unittest.cc)). This logic lives in Chrome's browser layer, not the generic WebAuthn content API.

Electron does not document equivalent extension RP-ID behavior. Treat it as **unsupported until an exact Electron 44 probe succeeds**. A renderer JavaScript shim must not bypass RP-ID validation because it is an access-control boundary. If absent, the proper fix is an Electron upstream change or a carefully reviewed Chromium/Electron fork implementing the same permission rules.

`chrome.webAuthenticationProxy` is not a generic password-manager provider API. Chrome documents it as a remote-desktop API that suspends normal WebAuthn handling and forwards ceremonies to a remote client ([Chrome WebAuthentication Proxy API](https://developer.chrome.com/docs/extensions/reference/api/webAuthenticationProxy)). Electron's permission feature file recognizes the permission, but its public extension support table does not promise the namespace. Even if a runtime probe finds it, it does not replace Bitwarden's injected provider architecture.

## What can and cannot be solved without forking Electron

### Strong candidates for application-level shims

- Toolbar actions, badges, action popups, and active-tab gestures.
- Commands and shortcut management.
- Extension context-menu registration and dispatch.
- The missing tab/window model and lifecycle events.
- Downloads and cookies through existing Electron main-process APIs.
- Side-panel hosting and offscreen-document lifecycle.
- `storage.session`, a local-only compatibility mode for `storage.sync`, and policy-backed `storage.managed`.
- Interactive OAuth windows (`identity.launchWebAuthFlow`-like behavior).
- Native messaging, provided it implements Chrome's host registration and allowlist security model rather than arbitrary process execution.

### Likely to require upstream or a maintained Electron/Chromium fork for full fidelity

- Chrome's extension-aware WebAuthn RP-ID and authenticator integration.
- Complete DNR semantics and high-performance request matching integrated at Chromium's extension/network layers.
- Chrome-profile `identity.getAuthToken` and Google account services.
- Private Chrome APIs, component-extension APIs, enterprise-only APIs, Chrome Web Store private installation APIs, and Chrome UI pages.
- Any API whose correct behavior requires Chrome's `Profile`, `Browser`, `TabStripModel`, Safe Browsing, sync, policy, or platform credential services rather than an Electron equivalent.

Electron's v44.7.2 source makes this boundary concrete: it registers a small Electron-specific function set, explicitly substitutes unsupported Web Store functions, and supplies custom tabs/messaging delegates rather than linking the whole Chrome browser product ([Electron API provider](https://raw.githubusercontent.com/electron/electron/v44.7.2/shell/browser/extensions/electron_extensions_browser_api_provider.cc), [Electron tabs implementation](https://raw.githubusercontent.com/electron/electron/v44.7.2/shell/browser/extensions/api/tabs/tabs_api.cc), [Electron messaging delegate](https://raw.githubusercontent.com/electron/electron/v44.7.2/shell/browser/extensions/electron_messaging_delegate.cc)).

## Recommended implementation order

1. **Build a behavioral conformance harness.** Generate MV2 and MV3 fixtures that call every required method, listen for every event, exercise worker sleep/wake, and verify browser-visible effects. Record namespace presence, call results, `runtime.lastError`, events, and state after restart. Loading without warnings is not a pass.
2. **Complete the browser model first.** One authoritative main-process registry should map Chromecraft windows, tabs, active tab, extension pages, and extension IDs. Actions, commands, context menus, side panels, tabs, and windows must share it.
3. **Create a least-privilege extension bridge.** Support extension pages, content-script isolated worlds where necessary, and MV3 service workers. Validate identity and permissions in the browser process. Never expose generic Electron IPC.
4. **Implement action/browserAction/pageAction fully.** This unlocks the primary UI and `activeTab` path for password managers, blockers, translators, capture tools, and developer utilities.
5. **Implement tabs/windows plus lifecycle events.** Many extensions load but silently malfunction without `onCreated`, `onUpdated`, `onActivated`, `onRemoved`, and focus/current-window semantics.
6. **Add commands and context menus.** They are core interaction paths for password managers and productivity extensions.
7. **Add cookies, downloads, sidePanel, offscreen, and storage areas.** Each needs permission, isolation, persistence, and cleanup tests.
8. **Design one network arbiter for Electron webRequest, extension webRequest, uBlock, and DNR.** Establish ordering and conflict policy before adding DNR rules.
9. **Implement native messaging as a hardened subsystem.** Test Windows and Linux host registration separately.
10. **Patch the engine-level gaps.** Add exact tests for extension-page WebAuthn foreign RP IDs and PRF, then upstream or fork the correct browser-process delegate behavior. Do the same for DNR if the application-level rule engine cannot meet Chrome semantics.
11. **Test real extensions, not only fixtures.** At minimum: Bitwarden, uBlock Origin/uBO Lite, a download manager, a side-panel extension, an OAuth-based extension, a native-messaging extension, a command/context-menu-heavy extension, and a developer-tools extension. Test install, update, disable/enable, restart, incognito/session isolation, and removal on both Windows and Linux Mint.

## Acceptance criteria for a compatibility claim

“Fully compatible” should require all of the following for a targeted extension and version:

- No unsupported manifest/API warning that affects a used feature.
- Its MV2 page or MV3 worker starts, sleeps, wakes, updates, and restarts correctly.
- Content scripts execute in the correct frames/worlds and obey host permissions.
- Messaging and long-lived ports survive expected lifecycle transitions.
- Every used API returns Chrome-compatible values and emits the expected events.
- Toolbar, popup, command, context-menu, side-panel, tab/window, download, cookie, and permission UI behave correctly where used.
- Network modification composes correctly with uBlock and Chromecraft's own handlers.
- Native messaging and identity flows enforce the same trust boundaries as Chrome.
- Passkey creation/get flows are tested with extension interception enabled, cancellation/fallback, conditional UI where used, PRF where used, and extension-page login/unlock.
- Behavior passes on packaged Windows and Linux Mint builds, not only Forge development mode.
- A failed or removed extension leaves no worker, hidden page, popup, native process, listener, shortcut, or privileged state behind.

No finite suite can prove compatibility with every future extension. The defensible product claim is a versioned compatibility target backed by API conformance results and real-extension matrices. On unmodified Electron, claiming universal Chrome compatibility would contradict Electron's explicit support policy and its own unsupported stubs.
